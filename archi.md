# `archi.md` — terraform-provider-vcp

> Архитектурный контракт репозитория. Кратко: границы, ограничения, контракты.
> Межрепозиторные рёбра — только в `workspace.yaml` корня workspace.

## 1) Context ID / Owner / Repository mapping

| Context ID | Owner | Repository | Code paths |
| --- | --- | --- | --- |
| ctx_terraform_provider_vcp | team/arch-owner | terraform-provider-vcp | main.go, internal/provider, internal/services, internal/locks, internal/acctest, examples, docs, scripts, .goreleaser.yml, .github/workflows |

Репозиторий одноконтекстный: провайдер, его ресурсы и обвязка acceptance-тестов —
один контекст; сборка релиза (`.goreleaser.yml`) и пайплайн (`.github/workflows`)
принадлежат ему же. `docs/` — генерируемый артефакт этого же контекста.

## 2) Boundaries (in/out of scope)

- In scope: ресурсы и data sources провайдера `vcp` (`internal/services/**`),
  их схемы, plan-модификаторы, валидация конфигурации, импорт и дрейф;
  реестр провайдера и его собственная схема (`internal/provider`);
  сериализация мутаций по родительскому объекту (`internal/locks`);
  примеры (`examples/`), из которых рендерится справочник (`docs/`);
  обвязка и sweeper'ы acceptance-тестов (`internal/acctest`);
  публикация провайдера в Terraform Registry по git-тегу.
- Out of scope: HTTP-клиент контракта `public-api` и его типы — они живут
  в `vstack-cloud-panel-sdk`, и дефект клиента чинится там, а не обходится здесь;
  доменные правила и валидация услуг (владелец — `cloudmng`); остальные внешние
  API монолита (`partner-api`, `referral-api`, Admin API v3); генерация кода
  из OpenAPI — схемы ресурсов пишутся руками.
- Primary L1 context: `ctx_terraform_provider_vcp`; Affected L1 contexts: нет.

Внутри контекста уживаются два продукта с раздельными каталогами и семействами
задач: vStack (строковые id, `TaskID`) и VMware Cloud (`vcp_vmware_*`, целочисленные
id, `VmwareTaskID`). Общего у них только слой провайдера и блокировки.

## 3) Layering constraints

- Слои: `main.go` → `internal/provider` → `internal/services/<семейство>` → SDK.
  `main.go` поднимает plugin-сервер; `internal/provider` — схема провайдера,
  конфигурация клиента и единственный реестр ресурсов и data sources;
  `internal/services/<семейство>` — схема ресурса, маппинг в модель, CRUD.
- Разрешено: пакету услуги зависеть от `internal/locks` (сериализация мутаций)
  и, в тестах, от `internal/acctest`; получать клиент SDK через `Configure`.
- Запрещено:
  - собственный HTTP-вызов, переобъявление типа SDK и правка декодированного
    значения под форму, которую SDK должен был вернуть, — недостающее
    добавляется в SDK;
  - ресурс или data source без строки в `internal/provider/provider.go` —
    незарегистрированного не существует;
  - импорт одного пакета `internal/services/*` из другого: семейства ресурсов
    независимы, общее выносится в `internal/`;
  - мутирующий путь без блокировки родительского объекта (`internal/locks`):
    платформа сериализует изменения одного объекта, Terraform применяет ресурсы
    параллельно;
  - смешивание `TaskID` и `VmwareTaskID`;
  - правка `docs/` и `vmware_acceptance_configs.md` руками — оба генерируются;
  - `replace` на локальный SDK в `go.mod` и коммит `go.work`.

## 5) Quality gates and testing

- Tests: unit-тесты на схему, маппер и обещанные пользователю валидации —
  Required, лежат в пакете самого ресурса; для путей, которые на живом стенде
  стоят машины и минут (частично применённый набор правил, ответ без
  необязательного поля, исчезнувший объект), — фейковый API
  (`internal/services/vmware/fakeapi_test.go`), воспроизводящий **проводную**
  форму ответа, а не форму DTO: publisher выбрасывает null-поля, и тест на
  форме DTO не дошёл бы до ветки, которую проверяет. Acceptance-тесты —
  Required на каждый ресурс и покрывают жизнь ресурса, а не один apply:
  создание → пустой план сразу после → правка на месте с проверкой, что объект
  не пересоздан → проверка пересоздания там, где оно обязано быть → импорт →
  дрейф при внешнем изменении → внешнее удаление → destroy; имена `test-acc-*`,
  иначе `make sweep` их не уберёт.
- Gates: `gofmt -l .` (пусто); `make vet` (`go vet ./...`); `make lint`
  (`golangci-lint` версии, приколоченной в `Makefile`, конфиг `.golangci.yml`);
  `make test` (unit-тесты, без учётных данных и без обращений к облаку);
  `make docs-generate` — после него `docs/` без диффа; `terraform fmt -check
  -recursive examples/` — `examples/` рендерится в `docs/`; `make check-release`
  (`GOWORK=off go build ./...`) — доказывает, что версия SDK в `go.mod`
  опубликована и `replace` не просочился; `make validate-configs` — реальный
  `terraform validate` по примерам и acceptance-конфигурациям против собранного
  бинаря.
- Pipeline: `.github/workflows/test.yml` гоняет те же гейты (сборка, `gofmt`,
  golangci-lint той же версии, `terraform fmt`, unit-тесты, отдельная job на
  актуальность `docs/`); `.github/workflows/release.yml` — goreleaser по тегу
  `v*`. Acceptance-тесты пайплайн не запускает: им нужны живые `VCP_*` и они
  создают тарифицируемые ресурсы (см. Known legacy deviations).
- Done: гейты зелёные; новый ресурс или data source зарегистрирован
  в `internal/provider/provider.go`; у него есть пример в `examples/`
  и сгенерированная страница в `docs/`; acceptance-тест написан и прогнан
  вручную; описание схемы написано как документация — предупреждение
  «это пересоздаёт объект» / «этот apply теряет данные» абзацем `~>`;
  новое подавление линтера — с обоснованием.

## 6) Known legacy deviations

| Deviation | Impact/Risk | Mitigation plan |
| --- | --- | --- |
| «109 применимых операций из 109» — счёт покрытия **возможностей**, а не прямых вызовов маршрутов. Прямого вызова нет у семи маршрутов: `GET /domains/{name}/records/{id}`, `GET /servers/{id}/volumes`, `GET /servers/{id}/volumes/{id}`, `GET /vmware/servers/{id}/volumes/{id}` (провайдер читает эти объекты списком родителя или из самого родителя), `PUT /servers/{id}` (покрыт `PATCH` — функциональным надмножеством), `PUT /vmware/networks/{id}/edge/bandwidth` (та же полоса ставится `EditVmwareNetwork`), `POST /vmware/networks/{id}/servers` (императивный bulk-дубль ресурса `vcp_vmware_server_network_attachment`) | дыр в пользовательских возможностях нет, но счёт «109 из 109» звучит как покрытие маршрутов и в этом виде неверен; читатель, сверяющий провайдер с контрактом маршрут за маршрутом, найдёт расхождение | называть счёт покрытием возможностей везде, где он приводится; при появлении новой операции контракта сверять не число, а возможность — маршрут без прямого вызова допустим только тогда, когда его результат уже достижим декларативно |
| 23 операции контракта в декларативную модель не ложатся принципиально — среди них питание серверов и шлюзов, `rollback`/`restore`, чтение задач, расчёт цены, `verify`, `rebuild` | провайдер не покрывает часть API, и это видно при сравнении с CLI, который покрывает её целиком | оставлено намеренно: это императивные действия и разовые запросы, их правильная проекция — computed-поля состояния, а не собственный ресурс. Пересмотреть, если платформа начнёт выражать такое состояние декларативно |
| `vcp_vmware_server` создаётся двумя способами — заказом из образа и копией существующей машины (`copy_from_server_id`); ветвление живёт в `Create` | формальный признак GR-01: набор полей меняет ход операции | оставлено намеренно: это один ресурс в одном состоянии, у которого два способа возникнуть, а не две операции. Разведение на второй ресурс дало бы два типа для одной машины и сломало бы импорт. Ветвление удерживается на плане: `ValidateConfig` и `ModifyPlan` отказывают в order-time аргументе рядом с `copy_from_server_id`, так что до `Create` доходит один из двух разобранных случаев |
| Acceptance-тесты, обязательные по правилам репозитория, ни одним пайплайном не запускаются: им нужны живые `VCP_*` и они создают тарифицируемые ресурсы | регресс, который ловится только acceptance-тестом (вечный diff, ошибочное пересоздание), в CI не виден; полагаться приходится на ручной прогон перед релизом | покрывать фейковым API всё, что он в состоянии поймать; при появлении стенда с квотой — отдельный планируемый пайплайн |
| Гранулярность пакетов разная: у vStack пакет на семейство ресурсов (`server`, `gateway`, `server_snapshot`, …), у VMware Cloud один пакет `vmware` на весь продукт | в `vmware` лежат все ресурсы продукта, и общие для них хелперы не отделены от частных; граница внутри пакета держится только именами файлов | новые ресурсы VMware класть в тот же пакет, пока продукт не разъедется по семействам; разделение — отдельной карточкой, оно ломает пути тестов и `make testacc-service` |

## 7) Change policy and required reviews

- Policy: новый ресурс или data source регистрируется в `internal/provider/provider.go`
  и получает пример в `examples/`; имена и семантика опубликованных атрибутов
  не меняются; `docs/` обновляется генератором, а не руками; недостающее
  в клиенте API добавляется в SDK и пиннится опубликованной версией
  в `go.mod`; поле, которое API принимает и игнорирует, не заводится.
- Required reviews: владелец контекста; интеграции — при добавлении раздела
  контракта `public-api` в провайдер и при смене версии SDK.
- Escalation triggers: переименование или смена смысла опубликованного ресурса,
  data source или атрибута (ломает пользовательский state); HTTP-вызов
  в обход SDK; мутирующий путь без блокировки родителя; смена major-версии
  провайдера; расширение исключений в `.golangci.yml`.
